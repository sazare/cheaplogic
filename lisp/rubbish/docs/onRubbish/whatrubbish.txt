Rubbishのまとめ

0. 今の視点

論理式の集合Σに対して、そこから証明できる矛盾(反証)のすべてが、Σの含む情報を表しているのではないだろうか。

前提として、resolution principleによる反証法を考えているので、一般的にはおかしな言い方になっている。

Σの反証の全体をΠ(Σ)と書くことにする。pは証明。

Π(Σ) = {p : Σ ⊢ □ }

これがΣに内在する情報だと考える。
この情報の構造とか特徴を知りたい。

そこで、
exhaustive proof : Σのすべてのclauseを一度だけ使って得られる矛盾の証明のこと。
を考える。(一般的な論理式の証明の場合は、Σ, ¬α⊢□と考えるからこれで十分だとおもうのだが)

exhaustiveな証明を考えると、制約がかかっているため、わかりやすくなる点がある。
たとえば、Resolutionだけを考えた場合は、すべてのリテラルには相手がいるので、+Pと-Pのリテラル数を数えると同じになる。数が違っていたらFactoringが必要であるということになる。


Σ'の矛盾の証明(反証)p

p : Σ' ⊢ □

について、証明にでてくるresolutionやfactoringのペアの集合を考える。
証明の順番が違っていても証明はこのpairの集合が同じなら同じだとみなしたい。

証明に出てくるliteralはすべて元のclauseのliteralを元に考えると、
このペアの集合は一意になり、まさに証明の情報になるのではないか?

しかし、p が複数あるとき、exhaustiveだからといって全部同じ情報にはならない。
だからΣ'の情報は一意にはならないだろうが、そういう特別な□ を集めれば近づけることができ
るのではないか?


[歴史]
　最初はresolution refutationのproverをつくろうと思っていた。
　総当たりのproverで、条件を指定してそこまで実行するものを作った。

　次にgoalをもとに証明を追跡する gtrail.asdを作成した。
  
  □のproofの順番が違っていても変わらないものは何かを考えた。
　input cid/lidのpairの集合はある程度変わらないと思った。
　これをpcode, p2codeと呼びツールを作成した。

  このあたりから、Σに含まれる全□ の証明情報がΣの情報だと考えるようになった。

　この場合、従来のproverによってひとつの□ をみつけるだけではたりない。
  全部の□ を検索するproverはいまいちな気がしていたが

　clause set Sの全clausesを使ってできる□ の証明(exhaustive proof)というものを考えた。
  Sから生まれる□ の情報がuniqueであるとは限らないし、あらかじめそれを考慮したperoofを作ることもできないだろう。
　しかし、given Σの矛盾構造を調べる手段にはなるのではないだろうか。
　つまり、与えられたΣの(すべての)部分集合についてexhaustiveな□ proofを考えると、Σに含まれる矛盾情報についての知識を増やせるのではないかと考える。


　これが可能になったのは、rubbish proverの方法が適していたと考える。

2025/11/28の段階では、exhaustive proverの実装において、Factoringをもれなく行うための仕組みができていない。
